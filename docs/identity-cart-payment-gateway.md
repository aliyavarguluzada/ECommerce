# Identity, Cart, Payment, and Gateway

## Current scope

Implemented with separate Domain, Application, Infrastructure, and API projects
for Identity, Cart, and Payment. ECommerce.Security shares token validation and
service authentication; API Gateway uses YARP to forward public routes. Each
service owns its PostgreSQL database.

Automated authentication, API, application, gateway, and HTTP checkout integration
tests now run locally; see [Automated tests](testing.md). Live PostgreSQL migration
application and container runs remain unverified here.
Message queues and outbox logic remain deferred.

Payment currently uses a clearly labelled development provider. It neither accepts
card data nor charges/refunds real money. Production disables this provider and
returns 503 until a production provider is implemented. IPaymentProvider is the
extension point; the current method-token contract must also be extended for a
real provider. Email confirmation, forgotten-password email delivery, MFA, tax,
discounts, shipping charges, returns, and carrier APIs are not implemented.

## Development configuration

Local signing credentials and service keys are generated by:

```powershell
./scripts/Initialize-Development.ps1
```

This has already been run in the current workspace. It creates Git-ignored
security.local.json, identity.private.json, and .env. It refuses to overwrite
existing files, so restarting services does not rotate keys or invalidate sessions.
No users or administrator accounts are created by the script. These files are also
excluded from Docker build contexts.

Access tokens use RSA/RS256. Identity alone loads the signing private key;
other services validate using Auth:PublicKey. Public/private keys are base64-encoded
DER keys. The local configuration file supplies issuer ecommerce-identity, audience
ecommerce, and development service keys. Docker injects the public key into each
API and the private key only into Identity.

Incoming trusted service credentials use X-Service-Key. Configure the receiver's
ServiceAuth:Keys:CallerName and the caller's ServiceAuth:OutgoingKey. Policies
restrict Cart, Order, and Payment credentials to their intended internal routes.
The gateway strips caller-supplied service/user headers and blocks internal path
segments. Internal calls go directly between services, not through the gateway.

## Identity

| Method | Route | Access |
| --- | --- | --- |
| POST | /api/identity/register | Anonymous; creates Customer |
| POST | /api/identity/login | Anonymous |
| POST | /api/identity/refresh | Possession of valid refresh token |
| POST | /api/identity/logout | Current customer; revokes refresh family |
| POST | /api/identity/logout-all | Current customer; revokes all refresh sessions |
| GET | /api/identity/me | Current customer profile |
| PUT | /api/identity/me | Update own display name |
| POST | /api/identity/change-password | Current password and new password |
| PUT | /api/identity/users/{id}/admin | Admin role management |

Passwords use ASP.NET Core Identity hashing. Passwords must contain at least 12
characters, including uppercase, lowercase, digit, and a non-alphanumeric
character. Failed sign-ins lock an account after five attempts for 15 minutes.
Anonymous identity endpoints are rate-limited per remote address. Behind the local
gateway this remote address is the gateway; production proxy/rate-limit configuration
will need deployment-specific tuning.

Access tokens last 15 minutes by default, configurable from 1–60 minutes.
Refresh tokens are random 64-byte values; only SHA-256 hashes are stored. Refresh
rotates the token and revokes its predecessor. Reusing a revoked token revokes its
whole token family. Refresh, logout, password changes, and role changes serialize
through user-specific database locks. Password/role changes revoke refresh sessions.

Logout and role changes do not immediately invalidate existing access tokens:
their old permissions remain until the access token expires (plus 30 seconds of
clock skew). Immediate distributed token revocation is not implemented. Obtain a
new login after a role change.

The first administrator is an explicit bootstrap operation after Identity migrations:

```powershell
$env:BootstrapAdmin__Email = 'your-admin@example.com'
$env:BootstrapAdmin__Password = 'CHOOSE-YOUR-OWN-STRONG-PASSWORD'
dotnet run --project ECommerce.Identity.Api --no-build --no-launch-profile '-p:Platform=AnyCPU' -- --bootstrap-admin
Remove-Item Env:BootstrapAdmin__Email, Env:BootstrapAdmin__Password
```

The bootstrap only creates a new account and assigns Customer/Admin roles.
It refuses to promote an existing account; use the authenticated administrator API
for that. No bootstrap credentials are committed or generated automatically.
Administrators cannot demote themselves.

## Authorization across services

- Catalog reads remain anonymous; mutations require Admin.
- Inventory stock initialization, adjustments, balances, and history require Admin.
- Inventory reservations require Admin or the trusted Order service credential.
- Public Order creation derives CustomerId from the authenticated token.
- Customers list/read/cancel/retry their own orders; administrators may inspect all.
- Shipping, delivery, and manual confirmation require Admin. Confirmation requires
  recorded successful payment; Admin does not bypass that business rule.
- Cart always belongs to the authenticated customer.
- Customers read/pay their own orders and payment receipts; administrators may
  inspect payment receipts.
- Cart can call internal Order creation/read routes.
- Payment can call internal Order read/payment-confirmation routes.
- Order can call Payment's internal refund route.

Public Order creation no longer accepts a client-controlled CustomerId. The
internal Cart contract still includes it, and Cart derives it from the token.
Internal Order reads return a minimal order summary rather than the shipping address.

## Cart

| Method | Route | Purpose |
| --- | --- | --- |
| GET | /api/cart | Own cart with refreshed Catalog quote |
| PUT | /api/cart/items/{productId} | Set absolute quantity |
| DELETE | /api/cart/items/{productId} | Remove line |
| DELETE | /api/cart | Clear editable cart |
| POST | /api/cart/checkout | Create/replay checkout |
| POST | /api/cart/checkout/retry | Resume own pending checkout from its stored snapshot |

Each customer has one persisted cart, up to 100 distinct products, with quantities
1–100000. Display quotes use current Catalog prices. Missing/discontinued products
remain visible but make CanCheckout false. Mixed currencies prevent checkout.
Order always recalculates and stores authoritative prices during checkout.

Checkout saves a request-ID-keyed item/address snapshot and freezes the cart before
calling Order. Repeating the same request/address resumes that snapshot. A timeout
does not clear the cart or permit a new order ID while the outcome is unknown.
A successful Order response, including accepted PendingInventory, clears only the
corresponding frozen cart snapshot. Known Order rejection marks the attempt failed
and unfreezes the cart; use a new request ID after fixing the cart.

A completed checkout may be replayed after new items are added: it returns its
original order without clearing the newer cart contents. Concurrent checkout
execution and cart editing serialize under the customer's database lock.

## Development Payment

| Method | Route | Purpose |
| --- | --- | --- |
| POST | /api/payments | Pay owned reserved order with RequestId |
| GET | /api/payments/{id} | Owned receipt, or Admin |
| GET | /api/payments | Own paginated receipts, or Admin filtering |
| POST | /api/payments/internal/orders/{orderId}/refund | Order service only |

Pay requests supply RequestId, OrderId, and MethodToken. Amount, currency, and
customer are taken from the Order summary. RequestId is the payment ID and
provider idempotency key. Replaying the same request does not charge twice.
Reusing it for another method/order/customer returns 409. There is at most one
non-failed payment per order. After a declined payment, use a new request ID for
another development attempt.

Development method tokens:

- dev-approved records a simulated successful payment.
- dev-declined records a simulated decline (HTTP 402).

No other method tokens, PANs, CVCs, bank credentials, or real-card data are accepted.
Receipts label the provider Development (no real charge). This provider is enabled
only when ASPNETCORE_ENVIRONMENT=Development and Payments:Provider=Development.

A durable successful receipt is saved before notifying Order. Notification
records the exact payment ID/amount/currency and begins inventory commitment.
Order reaches Confirmed only after successful payment and stock commitment.
A 202 receipt means payment or order notification is pending; inspect it by its ID.

Cancellation before shipping releases/restores stock and requests a full
development refund. The refund completes before the Order reaches Cancelled.
If an order is cancelled while payment completion is uncertain, Payment compensates
a late simulated success by refunding it instead of confirming the cancelled order.

A database-backed PaymentRecoveryWorker resumes pending payments, refunds, and
order notifications. Configure PaymentRecovery:Enabled and IntervalSeconds
(default true and 30). No payment transaction is held while calling Order's payment
callback, so cancellation can call Payment back for a refund without a lock cycle.

## Gateway

Local address: http://localhost:5100. Public routes retain their original paths:

- /api/identity/*
- /api/categories/* and /api/products/*
- /api/inventory/*
- /api/orders/*
- /api/cart/*
- /api/payments/*

Identity and Catalog read routes can be anonymous; downstream Catalog mutations
still enforce Admin. Cart, Order, and Payment routes require Customer.
Inventory routes through the gateway require Admin. Every backend enforces its
own authorization even when called directly. Internal routes are blocked at the
gateway; caller-supplied service credentials are removed.

YARP destinations live under ReverseProxy:Clusters in appsettings.json and may
be overridden with environment variables. Gateway requests are rate-limited to
300/minute per remote address. Cors:Origins is an explicit list (development default
http://localhost:3000); wildcard credentialed CORS is not enabled. JWT authorization
headers are forwarded to backends. /health/live is public.

ECommerce.ApiGateway/ECommerce.ApiGateway.http contains the complete authenticated
development checkout flow, with placeholder tokens and IDs.

## Databases and migrations

Services own catalog_db, inventory_db, order_db, identity_db, cart_db, and payment_db.
The new migrations include ASP.NET Identity tables, refresh sessions, carts/checkout
snapshots, payments, and Order payment fields. They are generated but not applied.

```powershell
dotnet build ECommerce.slnx '-p:Platform=Any CPU'
dotnet run --project ECommerce.Identity.Api --no-build --no-launch-profile '-p:Platform=AnyCPU' -- --migrate
dotnet run --project ECommerce.Cart.Api --no-build --no-launch-profile '-p:Platform=AnyCPU' -- --migrate
dotnet run --project ECommerce.Payment.Api --no-build --no-launch-profile '-p:Platform=AnyCPU' -- --migrate
dotnet run --project ECommerce.Order.Api --no-build --no-launch-profile '-p:Platform=AnyCPU' -- --migrate
```

Apply Catalog and Inventory migrations as described in their documentation.
Identity migration mode also initializes Customer/Admin roles.

Legacy orders confirmed before Payment integration may lack PaymentId. They cannot
be treated as paid or shipped under the new rules; reconcile legacy development
data explicitly rather than fabricating payment receipts.

## Running and Docker

Local backend ports: Catalog 5171, Inventory 5172, Order 5173, Identity 5174,
Cart 5175, Payment 5176. Gateway is 5100. Use the http launch profile locally to
keep service-to-service development calls consistent.

```powershell
docker compose up -d postgres
docker compose build
docker compose run --rm --no-deps identity --migrate
docker compose run --rm --no-deps catalog --migrate
docker compose run --rm --no-deps inventory --migrate
docker compose run --rm --no-deps order --migrate
docker compose run --rm --no-deps cart --migrate
docker compose run --rm --no-deps payment --migrate
docker compose up -d
```

A new volume initializes all service databases from docker/postgres/init-databases.sql.
An existing volume will not run that script again. Create any missing identity_db,
cart_db, and payment_db with psql using the volume's existing credentials, preserving
Catalog/Inventory/Order data. Compose requires the Git-ignored .env file for signing
and service credentials. Only Identity receives the private signing key.

Use environment variables or secret management for non-development deployments;
the generated local secret files are development conveniences. HTTPS, real payment
provider integration, email delivery, and deployment verification remain separate
work. See [Automated tests](testing.md) for authenticated integration coverage.
